# Test vectors

Checked-in known-answer vectors consumed by the CTest suite.  Vectors emitted
by external oracles are documented in [../../docs/TEST_ORACLES.md](../../docs/TEST_ORACLES.md);
they are generated by separate processes and never linked or ported.

- `xeddsa_libsignal.vec` (generated by `tools/oracles/xeddsa_libsignal`) -
  XEdDSA sign/verify KATs from libsignal.  Absent until first generated;
  `tests/core/test_xeddsa_vectors.c` skips the oracle KATs when it is missing.
- `x3dh_libsignal.vec` (generated by `tools/oracles/x3dh_libsignal`) - X3DH
  DH-stage (DH1..DH4) KATs from libsignal's X25519 (D-GEN-6).
  Absent until first generated; `tests/kex/test_x3dh_vectors.c` skips when it is
  missing.  libsignal cannot emit the assembled SK or KDF info, so only the DH
  stage is cross-checked (see TEST_ORACLES.md).

Self-KATs are generated from geryon's own deterministic code paths (no oracle);
they are the authoritative regression pins for constructions Signal specifies
but does not deploy, so no external generator exists (D-GEN-6).

- `prekey_self.vec` (generated by `tests/kex/test_hybrid_prekey_vectors`) -
  prekey construction KATs (HYBRID_SPEC §11.2): per suite, EncodeEC / the hybrid
  public and identity encodings, the PKID over that encoding, the signed_data a
  prekey signature covers, the XEdDSA signature over it (geryon's in-house 25519
  layer, via the gy_xeddsa_sign_z deterministic core), and, for hybrid suites,
  the ML-DSA prekey context string INFO("prekey"), all over fixed input keys.
  The ML-DSA signature bytes are NOT pinned (a liboqs primitive; covered
  behaviorally by test_hybrid_prekeys).  Everything else is a pure byte
  construction (no curve/KEM primitive runs), so the bytes are geryon's alone.
  Generate by running the test with the file absent: it prints `NAME=` records to
  stderr; paste them into this file, then record the file's sha256 here.  With
  the file present the test asserts every record matches byte-for-byte.
- `x3dh_self.vec` (generated by `tests/kex/test_hybrid_x3dh_vectors`) - hybrid
  X3DH key-schedule KATs (HYBRID_SPEC §11.2): the four §3.1 combiners
  HDH = HASH(kem_ss || dh) over fixed inputs, the seed triple SK derives to with
  and without an OPK (the handshake through SK), and AD_first.  Combiner inputs
  are fixed literal bytes, so no curve/KEM primitive runs; only geryon's fusion
  ordering, KDF wiring, and AD layout set the bytes.  The test writes the file
  directly when absent (same generation flow as prekey_self.vec).
- `dr_hybrid_self.vec` (generated by `tests/ratchet_hooks/test_hybrid_dr_vectors`)
  - hybrid Double Ratchet frame KATs (HYBRID_SPEC §11.2): a seeded reference
  conversation of three steps each direction, including an ML-KEM refresh
  boundary and the KEM confirmation chain (Bob's first reply), plus
  skipped-message recovery.  The hybrid analogue of `dr_he_self.vec`: curve
  keypair and header salt fixed via the ratchet seams, ML-KEM keygen/encaps fixed
  via the FIPS 203 `_derand` entry points (standard-fixed, seed-driven, and VALID
  so frames round-trip through the confirmation).  Built by the ratchet_hooks
  harness (needs core `GY_TEST_HOOKS`); the test writes the file directly when
  absent (same generation flow as the other self-vecs).
- `dr_he_self.vec` (generated by `tests/ratchet/test_he_vectors`) - Double
  Ratchet header-encryption frames (D-DR-16/17) from
  a seeded reference conversation with both RNG seams fixed (ratchet keypairs
  from constant scalars, hdr_salt from a fixed counter).  Generate by running
  the test with the file absent: it prints `frameN=` records to stderr; paste
  them into this file, then record the file's sha256 here.  With the file
  present the test asserts every generated frame matches byte-for-byte.
